# 開発調査・プロジェクト進行：AI単独レビューシナリオ

- 版：0.1.0 / 2026-10-10
- **目的**：承認済みの公開設計と共有KBの整合・境界・退行を、**ユーザーへの追加質問なし**で検査するための実行可能なシナリオ。
- **実施方法**：AIがGitHubの現行文書を読取、下記の架空相談文に対する期待動作・根拠の記載を照合し、検査結果を保存。実利用者の機密データの作成・送信・削除・本番変更はしない。
- **対象正本**：[AgentOS-C共通標準](https://github.com/Yosio-DMZ-C/AgentOS-C/blob/main/docs/PROJECT_EXECUTION_STANDARD.md)、[一般設計書](https://github.com/Yosio-DMZ-C/AgentOS-C/blob/main/docs/AgentOS-C_%E8%A8%AD%E8%A8%88%E3%83%BB%E6%A7%8B%E7%AF%89%E9%81%8B%E7%94%A8%E6%8C%87%E7%A4%BA%E6%9B%B8_%E4%B8%80%E8%88%AC%E9%85%8D%E5%B8%83%E7%89%88.md)、[AI無課金版](https://github.com/Yosio-DMZ-C/AgentOS-C/blob/main/docs/AgentOS-C_%E8%A8%AD%E8%A8%88%E3%83%BB%E6%A7%8B%E7%AF%89%E9%81%8B%E7%94%A8%E6%8C%87%E7%A4%BA%E6%9B%B8_AI%E7%84%A1%E8%AA%B2%E9%87%91%E3%83%A6%E3%83%BC%E3%82%B6%E3%83%BC%E7%89%88.md)、[共有KBのプラクティス](../docs/DEVELOPMENT_WORKFLOW_PRACTICES.md)、[開発調査Skill](../skills/development-research/SKILL.md)、[共有KB運用規則](../docs/GOVERNANCE.md)。
- **状態の区別**：本文の整合とルールの机上判定は`DOC_PASS`。モデルが実際にそのように回答するか、月次ジョブが実行されるか、外部サービス操作が成功するかは**別の実機検証**であり、ここでは`NOT_RUN`。
- **禁止**：テストを名目に公開権限・課金・ユーザーデータを変更しない。実在ユーザーのファイルID・共有URL・NodeID・メールアドレス等を公開ログへ書かない。

## 0. 開始前の品質ゲート

次をすべて満たしてから文書レビューを`DOC_PASS`とする。

- Q1：実在するmain上の対象ファイルを読戻し、リンク先が存在する。
- Q2：レビュー対象のGit blob SHAまたはコミットを明示し、将来の更新と混同しない。
- Q3：**必要な承認を迂回せず**、未決の枝だけ保留し、独立作業を続ける。
- Q4：スモーク／統合テストとConsumer/Provider契約テストの区別があり、文書検査を実運用のPASSと誤表示しない。
- Q5：現行の初期セットアップ、既存ID、無料版の基本範囲、共有KBのActive件数を破壊していない。
- Q6：公開差分に個人情報・非公開URL・トークンが入っていない。
- Q7：各シナリオの入力・期待動作・根拠・非実施境界を記録する。判定不能はFAIL/NOT_RUNとし、合格に数えない。

## 1. 架空入力による意思決定テスト（本人への質問不要）

各ケースは**実在しない利用者・架空の状況**を用いる。AIは文書を照合し、期待動作が規定されているか判定する。実際の本番サービスへ書込む必要はない。

|ID|架空入力／初期条件|期待動作・合格条件|
|---|---|---|
|S01|「毎日のメモをAIでDriveへ保存したい」／個人の一般メモ|使える接続を先に確認し、既知の公式仕様・過去結果を再利用。推奨構成1案、必要な操作と次の1操作を示す。|
|S02|「APIには更新機能があるらしい」／このチャットに書込ツールがない|API仕様上の能力と現在のAIの可用操作を区別。書込済みと主張しない。|
|S03|「Driveに架空メモ1件を保存・読戻しできた」|**実接続の小規模スモーク／統合確認PASS**と限定。Pact型契約テストPASS、Markdown完全復元PASS、別チャットPASSへ拡張しない。|
|S04|「接続サービスを全部検証して」／目的はMarkdownの整形だけ|外部接続を不要と判断し、対象を限定。既存資料から処理を開始し総当たり調査をしない。|
|S05|「開発手順を自動化して」／初回の同カテゴリ依頼|必須の検査は進めるが、2回目の事実がない限り「二度目」と断定しない。新規ツールを自動作成しない。|
|S06|同カテゴリの**独立した2回目の依頼**／履歴が確認できる|短くツール付き手順書を提案。利用者が承認するまでは新規ツール開発を始めず、現在の資料調査は続ける。|
|S07|「質問せず進めて、最後に変更と質問をまとめて」／一般の設計・レビュー作業|その依頼の`continuous`を適用。安全な調査・差分・検査を続け、最後に結果・保留・質問をまとめる。毎工程で停止しない。|
|S08| `checkpoint` が合意済み／複数の独立タスク|主要節目のみ確認。未承認の枝は保留し、並行可能な作業を進める。|
|S09| `stepwise` が合意済み／主要段階を終えた|必要な段階で確認し、返答を待たずに次の未承認段階へ進まない。|
|S10|自動継続で「課金・公開権限変更」と「文書の読取レビュー」が同時に必要|課金・公開操作のみ停止し、文書読取と机上レビューを継続。実行済みと偽らない。|
|S11|案件の進行方式が未設定／低リスクな資料整理に十分な情報がある|不用意な追加質問なしに可逆な作業を開始。大型の新規案件で方式選択が判断に影響するときだけ一度確認。|
|S12|過去の方式確認日が**31日前**／現在の進捗会話あり|この会話で方式継続を一度だけ尋ねる。未返信なら既存の権限内で継続する。過去確認が**15日前**なら再質問しない。|
|S13|前回の月次レビューから31日経過したがチャットの新規依頼も予約ジョブもない|背景で質問・処理したと主張しない。次回の自然な会話時に確認する。|
|S14|成果物の必須ゲートにFAIL・NOT_RUNが残った|対象成果物を完成扱いしない。別の合格した独立成果物を破棄せず、失敗した枝だけ止める。|
|S15|元のMarkdownを`.txt`で渡す要求／ダウンロード先がTXTのみ読める|中身を完全に保持して`.txt`を作り、「本文はMarkdown」と短く明記。形式・拡張子・復元手順を検査する。|
|S16|「記事のリンクを教えて」／公式の根拠が既知|検索結果の一覧だけでなく、実際の個別URLを示す。未確認URLを有効と断定しない。|
|S17|生Markdownで構成したKBの更新／Googleドキュメント読書き試験だけPASS|生Markdownの保存・NodeID・履歴保持は`NOT_RUN`。今回の狭い成功をKB全体の同期成功と扱わない。|
|S18|共有KBを正式Active化したい／独立した人間のレビュー記録がない|AI自己レビューを進めてDraftを保存できるが、**人間レビュー待ちをActiveと呼ばない**。|

## 2. AI単独で実行する確認手順

1. GitHubコネクタ等で2リポジトリのmainから対象ファイルとblob SHAを読取る。GitHubに接続できない場合は提供された取得時点固定のテキストを使い、実際にmainを検証したとは記さない。
2. S01〜S18に対し、**期待動作を実装している記述を探す**。現在の文書がその分岐を明示するなら`DOC_PASS`、欠落なら`FAIL`。表現が曖昧なら`WARN`（合否に関われば修正候補）。
3. Q1〜Q7を点検。GitHubの公開変更差分と現在のカタログを確認し、Active件数／初期承認／個人情報流入を照合する。
4. **欠落があっても大きな設計変更は自動で行わず**、具体的な最小差分と根拠だけ提案する。利用者が既に許可した軽微修正は変更・再検査できる。
5. 結果を日付・対象SHA・実施方法・PASS / FAIL / NOT_RUN・未検証事項つきで記録。個人KBや本番接続先を編集する必要はない。
6. 全件`DOC_PASS`でも**本番運用の成功、独立した第三者レビュー、定期実行の登録済み**を主張しない。

## 3. 実機検証を別扱いにする項目

次はAIが現在の会話で使えるツール・権限だけでは一般的な成功を保証できないため、今回の文書品質レビューとは分離する。

- 新規チャット間でのコネクタ継続、他の契約プラン・他AIの動作
- 本番の自動同期・外部公開・権限変更・課金
- 医療等の保護情報の適法性と組織承認
- 独立した人間の審査、長期の作業時間短縮効果
- 1か月先に予約ジョブなしで自動質問すること

## 4. 出力契約

報告は次の順にまとめる：**対象と版／QゲートとSシナリオのDOC_PASS・FAIL・NOT_RUN／重大な問題／変更候補／ユーザーへの質問**。最後の質問以外では進行停止を伴う確認をしない。現在の実行環境でできない検査は`NOT_RUN`とする。
