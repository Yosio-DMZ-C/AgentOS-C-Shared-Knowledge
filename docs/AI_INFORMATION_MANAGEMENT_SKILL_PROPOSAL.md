## 1. 解決したい問題

「会話メモを自動で整理したい」「毎回同じ情報を説明せずに済ませたい」「別AIでも同じKBを使いたい」などの希望に対し、各自がMCP、API、アプリ別連携、価格、権限、新規チャットの読み直し能力をゼロから調べると、導入前の検証が過度に重くなる。

**本Skillは新しいAPIを作るのではなく、確認済みの公開仕様・既知の相性・実例と失敗条件を再利用して、作業可能な最小構成を先に1案示す**ことを目指す。

### 対象となる典型例

- 日々の個人メモや会議メモをAIが要約・分類し、後で検索できるようにする
- ChatGPT / Grok / Claude等で生成したKBを、個人が管理する保存先に保管する
- Notion・Google Drive等を情報の正本として、読取・追記・更新・バックアップを整える
- 医療・法律などの専門職が、**所属組織の許可がある範囲で**事務メモ管理を省力化する構成を検討する

患者情報、顧客秘密、診療記録などの機微情報は、利用規約、組織の承認、保管場所、アクセス制御、対象地域の規制に適合した手段だけを候補にする。**未承認のAI・外部サービスに実データを入れて接続テストしない。** 技術的に接続可能であることと、業務で利用可能であることは別に判定する。

## 2. 初回応答の契約：利用者に検証作業を丸投げしない

AIは原則、利用者に次の **2点**を短く確認する（会話やKBから分かる項目は聞き直さない）。

1. **何をしたいか**：例「スマホのメモを整理してGoogle Driveへ自動保存」
2. **データの扱い**：個人の一般メモか、業務・医療等の保護が必要な情報か

利用者が使っているAI・保存先・契約プランが既に分かる場合はそれを利用する。不明で選択に影響する場合だけ、追加で**1件ずつ**聞く。

**最初の提案**は、1案を優先し、次の情報だけ簡潔に示す。

- 構成（例：チャットAI → 接続済みクラウド保存先）
- その時点で分かる「対応／制限／未確認」および出典と確認日
- 利用者の作業回数、必要な契約・費用、保存や復元の方法
- **次の1操作**（例：連携アプリの接続、またはまず架空メモ1件で試す）

**使える接続経路が確認済みなら、毎回MCPから調べ直す必要はない。** 詳細比較、代替構成、自作ツールの提案は、第一候補が適合しないか利用者が希望した場合に追加する。

## 3. 再利用する「接続制限カード」（共有KB側）

製品名だけで「連携可能」と結論しない。各カードの最小項目：

|項目|説明|
|---|---|
|`client` / `destination`|どのAIクライアントから、どのサービスへ接続するか|
|`method`|標準アプリ／MCP／API／Make等／人間による手動搬送|
|`plan_and_permissions`|料金区分、管理者許可、対象ページ・フォルダの権限|
|`operations`|検索・読取・新規作成・更新・削除・書出しのうち、**実際に確認された範囲**|
|`data_semantics`|上書き／追記／重複、ID、リンク、更新履歴、復元可能性|
|`session_behavior`|同一セッション内だけか、**新規チャットから再取得できたか**|
|`evidence_level`|**仕様上対応**／**独立した実動作確認**／**利用者環境で確認**／**未確認**|
|`source_url` / `checked_at`|正式仕様・制限事項の一次URLと取得日、必要なら旧仕様への注記|
|`limitations` / `fallback`|制限・停止条件・使えない場合の代替操作|

公開共有KBには**一般化できる仕様と架空データによる試験結果だけ**置く。Cookie、トークン、個人の共有URL、本人の非公開メモ、患者・顧客・組織の具体的な情報は置かない。

重要：MCP Registry等の**発見用カタログに名前があることは、現在のチャットが書込できる証拠ではない**。同様にNotionページの読書きが成功しても、Markdown階層型のKB・固定ID・履歴・添付ファイルを完全に保持できるとは限らない。

## 4. 判断の流れ（検証負担の最小化）

1. **目標と保護要件を確認**し、必要最小の構成を選ぶ。既知の公式仕様・公開カードを先に再利用する。
2. **能力と条件を照合**：現在のAIから必要な操作（読取／更新／バックアップ）ができるか、権限・プラン・地域・制約を分ける。仕様で確定済みの事項を再テストしない。
3. **構成を1案提示**：既存アプリ・低コスト・保守が容易・データを持ち出せる構成を優先する。直接接続が不可能なら、完全版ファイルの手動バックアップなどを提案する。
4. **未知の境界だけ小さく確認**：書込が必要なら、架空データ1件で「書く→読む→更新」を確認。別チャット運用が要件に入る場合だけ「新規チャットから読み戻す」試験を追加。復元が必須ならバックアップの再読込も検証する。
5. **合格した部分だけ採用**：未実施は `NOT_RUN`、不合格は `FAIL`。失敗時は元データを維持し、手動搬送・別サービスなどの代替1案へ戻す。

**すべての環境でフル検証を要求しない。** 求められる機能・リスク・既知の証拠に応じて試験を限定する。初期段階から大規模なワークフローエンジンやRAGを必須としない。

## 4.1 開発用調査の共通手順（調べ直しを減らす）

必要な機能・失敗時の影響を先に決め、**既存の調査成果を再利用して、不足分だけ調査する**。接続先ごとに別の重い調査プロジェクトを立てない。

1. **既知情報を先に探す**：この共有KBの接続制限カード → 公式仕様・変更履歴・料金と権限 → MCP等の互換一覧 → 実例の順で確認する。公式仕様と二次資料を区別し、古いカードは期限切れ・条件変更の有無だけ確認する。
2. **重要な選定だけ短いADRとして残す**：目的、比較した選択肢、採用・不採用理由、根拠URLと確認日、弱点、撤回／見直し条件を数行で記録する。結論が変わったときは旧判断を黙って消さずに後継へつなぐ。すべての小操作にADRを要求しない。
3. **必要な契約だけ検査する**：利用者の目的に必要な「検索・読取・追加・更新・再読込・復元」のうち、使う操作だけを対象にする。通常は架空の1件で十分。将来コード化する場合はPact等の**契約テストの考え方**を参照するが、Pactの導入自体は必須にしない。契約テストだけでは個人KBの意味・履歴・業務上の適法性を証明できない。
4. **既製の差分・再試行手段を優先する**：公式の変更追跡APIなどがある場合は自作の全件再走査より優先して調べる。ただし、APIの存在と現在のAIコネクタからの利用可能性は別。呼出回数制限には公式の `Retry-After` 等に従い、無限再試行・無確認の重複書込を避ける。
5. **再調査の条件を記録する**：接続カードに適用プラン、操作、出典、確認日、結果（PASS / FAIL / NOT_RUN）、既知の制限、再検証条件を残す。毎回全件を試験せず、仕様変更・失敗報告・プラン／権限の変化・期限切れ・高リスク用途のときだけ影響範囲を再確認する。

**効率の目安**：提案までの調査時間、利用者の手作業回数、追加費用、保守の負担、失敗時の復元容易性。調査や自作自動化が、節約できる工数を上回りそうなら採用しない。

### 調査手法の一次資料

- [AWS：Architecture Decision Records（ADR）の使い方](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html) — 判断背景・結論・影響と、決定履歴の保持
- [Pact公式：Contract Testing](https://docs.pact.io/) — 消費側が必要とする契約に検査対象を絞る
- [Google Drive：変更追跡](https://developers.google.com/workspace/drive/api/guides/about-changes) — 利用可能なAPIによる変更検出。コネクタ側の実装とは区別
- [Microsoft Graph：throttling](https://learn.microsoft.com/en-us/graph/throttling) — 429、`Retry-After`、バックオフなどの基本

## 5. 安全・権限の境界

- **記録の意味を変えない**：「検討」「購入」「所有」「在庫」「承認」「医療上の事実」を推測で変換しない。
- **自動実行を必要最小限に**：共有、公開、購入、外部送信、削除などの影響が大きい操作は本人の個別承認を要する。
- **秘密を公開しない**：連携URLやログに現れるトークン・Cookie等を共有カードへ転記しない。
- **復旧できない自動化を勧めない**：正本、バックアップ、失敗時の停止・やり直し方法を構成に含める。
- **業務や医療に使う場合**：データ保護、契約、管理者承認、監査・アクセス制御の条件を先に照合。未許可なら実データで試さず、架空データの概念実証に限定する。
- **本人の判断を尊重**：個人の時間削減と利用しやすさを重視し、AI導入自体を一律に義務化しない。

## 8. 今回の範囲と今後の判断

今回の成果物は**構想と検査設計**のみ。API操作、MCP接続、自動バックアップ、通知システムの実装はしない。

次工程ではまず**個人用の一般メモ → 既知の保存先への保存**という1本の低リスクな経路で評価する。新規のスクリプトや連携ツールは既存標準機能では解決できないことが分かり、再利用効果が開発・保守コストを上回るときに提案する。

このSkillはAgentOS-Cの一般導入に必須ではない。共有知としての参照と個人KBへの適用を分け、個人の入力情報や利用結果を共有リポジトリへ自動送信しない。
